# Документация по поддержанию жизненного цикла программного обеспечения

## Введение
Документ описывает, как сопровождается программное обеспечение «Обозреватель технической документации»: процессы разработки, выпуска версий, исправления ошибок, обновления и вывода из эксплуатации.

## 1. Процессы разработки
1.1. Задачи ведутся в бэклоге репозитория (Issues); у каждой задачи — оценка трудоёмкости.
1.2. Работа планируется спринтами по две недели; ежедневные стендапы не длиннее 15 минут.
1.3. Ветки: `main` — стабильная версия, `develop` — текущая разработка, `feature/<задача>` — новые функции, `bugfix/<задача>` — исправления. Слияние в `develop` и `main` — только через pull request с код-ревью.
1.4. Каждый коммит решает одну задачу и имеет информативное сообщение на русском языке.

## 2. Непрерывная интеграция
2.1. При каждом push и pull request GitHub Actions выполняет: проверку стиля (ruff), тесты сервера (pytest) на Linux и Windows для Python 3.11 и 3.12, проверку типов и сборку клиента (tsc, next build) на Linux и Windows, сборку Docker-образов и дымовую проверку сервера.
2.2. Артефакты сборки (код сервера, сборка клиента) сохраняются в GitHub Actions на 90 дней.
2.3. Уведомления о результатах сборки приходят авторам коммитов средствами GitHub.

## 3. Выпуск версий
3.1. Номер версии хранится в `backend/app/__init__.py` (`__version__`) и `frontend/package.json`; схема — семантическая: мажор.минор.патч.
3.2. Порядок выпуска: слияние `develop` в `main`, тег `vX.Y.Z`, сборка образов, обновление раздела «Изменения» в документации.
3.3. Схема базы данных создаётся при старте (`create_all`); изменения схемы, не покрываемые этим способом, оформляются скриптом в `backend/migrations/` с описанием в документации выпуска.

## 4. Исправление ошибок
4.1. Ошибка регистрируется в Issues с шагами воспроизведения, ожидаемым и фактическим результатом, журналом (`logs/app.log`) и версией.
4.2. Приоритеты: критический (блокирует работу) — исправление в течение рабочего дня в ветке `bugfix/*` от `main`; высокий — в ближайшем спринте; остальные — по плану.
4.3. На каждую исправленную ошибку добавляется автотест, воспроизводящий её.

## 5. Обновление экземпляра
5.1. Docker: `git pull && docker compose up -d --build`. Данные (база, журналы, индекс OpenSearch) хранятся в томах и сохраняются.
5.2. Установка из кода: остановить службы, `git pull`, `pip install -r requirements.txt`, `npm ci && npm run build`, запустить службы.
5.3. Перед обновлением выполняется резервное копирование по операционной инструкции.
5.4. После обновления проверяются `GET /api/health`, вход, поиск и ответ ассистента.

## 6. Поддержка окружения
6.1. Зависимости закреплены точными версиями (`requirements.txt`, `package-lock.json`); обновление зависимостей — отдельной задачей не реже раза в квартал с прогоном CI.
6.2. Журналы ротируются автоматически; индекс OpenSearch пересобирается командой «Переиндексировать» без потери данных (источник истины — база документов).

## 7. Вывод из эксплуатации
7.1. Выгрузить журнал аудита и журнал ИИ при необходимости хранения.
7.2. Остановить службы, сохранить резервную копию, удалить контейнеры и тома (`docker compose down -v`) либо папки `backend/data`, `backend/logs`.
